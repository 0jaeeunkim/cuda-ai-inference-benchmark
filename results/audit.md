## Experimental fairness and timing

**Shared workload.** Warm and application paths use the same pinned DistilBERT SST-2 model revision; GPU model is a deep copy of CPU weights. CPU/GPU inputs are the same token IDs and attention masks (shape, values and int64 dtype checked), all padded/truncated to sequence length 64. Model parameters are FP32, `eval()` and `torch.inference_mode()` are used, CPU intra-op threads are 8 (interop 16 recorded), matmul precision is `highest`, and CUDA/cuDNN TF32 are disabled. Correctness uses equal predicted class, finite output, and diagnostic logit comparison; a small logit delta is not a failure (maximum recorded absolute difference about 6.56e-6). The process-cold devices load the same pinned local model separately and use the same pretokenized input artifact; matching prediction checksums are an output equivalence check, not an independent weight hash.

**Warm primary.** CPU uses a host `perf_counter_ns` around forward, after CPU warm-up. CPU runs form a separate block before GPU pairs. GPU inference-only uses CUDA Events around forward with resident device inputs and synchronizes the end event before reading time. GPU E2E uses a synchronized host clock around blocking pageable H2D input copies, forward, pageable D2H logits copy, and final `torch.cuda.synchronize()`. The GPU input/output buffers are allocated before timing. Tokenization, model loading, allocation, correctness checks, and warm-up are excluded. The two GPU paths have the same forward tensors/model, but different invocation and timer boundaries; the difference of their medians is **E2E excess latency**, not isolated transfer time or a paired-difference median.

**Application validation.** The source enumerates exact, nonoverlapping spans through row 872. Forward counts for batches 1/8/32/64 are 872/109/28/14; final batch sizes are 1/8/8/40. CPU total host timing includes the forward loop. GPU E2E total host timing includes its loop, per-batch pageable H2D input and D2H logits copies, and final synchronization. Both exclude tokenization, model loading, correctness work, warm-up, and buffer allocation. CPU and GPU boundaries intentionally differ by GPU transfers. The five CPU runs precede five GPU runs at each batch; the large observed gap is robust, but order is a session-level confounder and no across-session uncertainty is measured. Timed outputs are not individually checked; the full-workload correctness pass occurs before timing.

**Process-cold v2.** The orchestrator launches each worker with `subprocess.run([sys.executable, worker])`: a fresh interpreter, not forked CUDA state. The worker's first `torch.cuda.*` call and its initialization check occur after the `total_job_ms` clock starts; each raw row reports an uninitialized context at that point. Untimed model-cache priming occurs before measured launches; this aims for process-cold/file-cache-warm conditions without proving identical physical OS cache residency. Model loading is local/offline and **inside** total job time, followed by timed GPU initialization, model transfer, GPU input-buffer allocation and synchronization; first and remaining forwards include GPU H2D/D2H and completion. Interpreter/import, input-artifact loading, tokenization, network and CPU output-buffer allocation are excluded. No worker warm-up occurs. Launch order alternates within N, but a 3:2 split at five coarse repeats and sequential N scan do not eliminate drift or order effects.

## Statistical audit and concerns

- Warm primary has 30 observations per path/batch. The largest individual/median ratio across all conditions is 1.041 (batch-2 CPU); no outlier exclusion is needed for the reported medians. E2E exceeded inference-only in 30/30 paired invocations at batches 1,2,4,16,32 and 29/30 at 8,64. The measured order effect remains visible: at batch 1 E2E position-1/position-2 medians are 1.282/1.292 ms. Pooling all 15 pairs of each order controls the main estimate's position balance; strata are diagnostic, not independent primary estimates. Thirty repeats describe one session, not day-to-day/device variation.
- Application validation has five repeats per path/condition; nearest-rank p95 is the largest of five, so it is a weak tail estimate. One full session and fixed CPU-before-GPU order limit uncertainty inference. The 872-sample result is consistent with warm scaling under its own timing boundary; it is not an independent cross-machine validation.
- Cold coarse has five fresh processes/device/N. It is adequate to identify the observed coarse median winner bracket but not a precise or stable threshold. A GPU-first launch effect of roughly 20–25 ms appears at N=1,8,32 in the recorded diagnostic strata. N=16 refinement balances order 5:5. N=16 median gap is 7.722 ms, below CPU IQR 20.618 ms and GPU IQR 26.723 ms; 10 repeats/device still do not locate an exact crossover. The observed-median winner changes between **16 and 32 samples/job**. No interpolation, probability-of-win claim, or exact crossing count is supported.
- **Material provenance issue:** the coarse and refinement session JSON `fixed_policy`/`policy` objects state `model_load_in_timed_interval=false` and `buffer_allocation_in_timed_interval=false`. These come from `benchmark_harness.check_policy()`, which describes the warm protocol. Actual `cold_start_worker.py` starts total timing before `from_pretrained()` and allocates GPU input buffers inside timed device preparation; `PROJECT_SPEC.md` §16A and the JSON `timing_boundary` strings agree with the code. This affects *machine-readable timing documentation*, not the raw total-job values or their reconstruction. **Remeasurement is unnecessary.** Minimum correction: append a separately hashed corrigendum keyed by the two session IDs that marks model load as timed, GPU input-buffer allocation as timed within device preparation, and CPU output-buffer allocation as excluded; then make future cold metadata use a cold-specific policy object. Preserve original JSON and raw files. Until then, presentations must cite the actual source/spec boundary and explicitly avoid those two flags.

## Claims allowed, claims rejected

**Five defensible central claims:**

1. Warm batch 1 GPU E2E median was **1.287 ms** versus CPU **10.950 ms** (**8.51×**); no CPU–GPU crossover was observed for either GPU path across tested batches 1–64.
2. Warm batch 64 GPU E2E median was **14.912 ms** versus CPU **460.802 ms** (**30.90×**). E2E throughput rose only **3.04%** and speedup **3.62%** from batch 32 to 64; this is diminishing gain, not diagnosed saturation.
3. For all **872 SST-2 validation samples**, GPU E2E total median fell from **1.094 s at batch 1** to **0.203 s at batch 64**; corresponding CPU totals were **9.582 s** and **6.286 s**, with **8.76×** and **30.97×** speedups.
4. Warm E2E excess over inference-only was **0.0323 ms (2.51%)** at batch 1 and **0.0501 ms (0.34%)** at batch 64. These are differences between distinct measured paths, not pure transfer measurements.
5. Process-cold CPU/GPU median total job was **114.224/279.144 ms at N=1** and **452.759/318.829 ms at N=32**. After N=16 refinement, the observed-median transition bracket is **16–32**, while its N=16 gap (**7.722 ms**) is below both device IQRs.

## Limitations, ordered by importance

1. One RTX 5080 / Ryzen 7 9700X server, one model and SST-2 validation pool; no general hardware or application conclusion.
2. Warm, full-workload, and process-cold total-job metrics have different timing boundaries and must not be pooled. Cold excludes interpreter/import and input load; it is not full machine/application cold start.
3. Fixed FP32/highest, TF32 off, 8 CPU threads, sequence length 64, pageable host memory, and one sample pool (nested prefixes for warm batches). Other configurations may reorder performance.
4. Warm/application each have one session; application has only five repeats/path/batch, making p95 the maximum. Cold coarse has five fresh runs/device/N and refinement ten; launch-order and file-cache effects remain.
5. No profiler or power/clock trace establishes GPU utilization, saturation, compute-boundedness, or the causal decomposition of E2E excess. The cold session metadata flags described above need a corrigendum for machine-readable reuse.

## Unresolved uncertainty and final M7 verdict

The exact process-cold crossover count, between-session stability, physical page-cache equality, and hardware cause of the warm 32→64 flattening remain unresolved. The cold JSON policy-flag inconsistency is **material to provenance but not to the measured claim**. No raw file, summary, plot, code, original hypothesis, or prior analysis was modified. **Conditional pass:** scoped presentation planning can proceed using the five claims above and the explicit timing definitions; repair cold machine-readable metadata with an append-only corrigendum before treating those JSON flags as authoritative or publishing reproducibility metadata. No remeasurement is required for this finding.
